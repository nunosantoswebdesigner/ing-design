Entry 01 — The problem

Every project reinvents the same button.

Without a single source of components, the cost of keeping products and brands consistent grows with every new project.

  • Duplicated components, slightly different from one project to the next
  • No direct bridge between the tokens defined in Figma and the code in production
  • Every new project starts the UI from scratch instead of installing what already exists
  • Visual inconsistency between brands that should share the same base

Customize this slide with 2–3 concrete, internally recognizable examples — a component already implemented differently across two projects, or a case of visual drift between brands. Real examples convince more than the generic list.

Entry 02 — What it is

One registry, one source of truth, many brands.

ING Design is a shadcn/ui component registry: installable via CLI, with the code living inside the consumer's project — not in a runtime dependency that updates from under you.

$ npx shadcn add https://ing-design.vercel.app/r/button.json
  • Registry — versioned source of truth, with prefixes by type (component / element / block)
  • Theming — a neutral base, with brand layers on top; already proven to work across different brands
  • Figma Diff — automatically checks whether the code still matches the tokens defined in Figma
  • Docs — every component documented, with preview, code, and design specs
Notes

The key point for a technical audience: unlike a shared npm package, the code is copied into the consumer's project at install time. That eliminates the classic "breaking change in a shared dependency" problem — every project owns its own code, but all of them start from the same source.

Don't center the conversation on the specific brands already supported or their names — what matters here is the multi-brand capability itself, not which brands exist today.

Entry 04 — Multi-brand

One base, as many identities as needed.

The same component structure, with a different visual identity per brand — without duplicating logic. Already validated with more than one brand.

Notes

What matters here isn't the specific brands already supported, but the capability: any new brand comes in as a layer on top of the base, without touching existing components.

Technical mechanism: a .theme-{name} class swaps the CSS variables (color, radius, typography). For most components, that's enough. But for the ones with genuine structural differences — button, card, table, dialog — dedicated per-brand files already exist in code, just not yet wired into the docs preview UI. That's item #1 in "what's missing" (entry 14).

Entry 06 — The keystone

Registering isn't paperwork. It's what connects everything.

While a component is just a loose file, it's just code. The moment it's registered, it becomes structured data — and structured data can be read by anything.

"name": "button", "files": [...], "dependencies": [...], "cssVars": {...}
Unlocks
Diff with Figma
Without the component's JSON and its cssVars, there's nothing to compare against Figma.
Unlocks
v0 / ChatGPT / Claude
The AI reads the registry entry's structure — it doesn't guess the component from loose code.
Unlocks
CLI installation
npx shadcn add only works because a manifest points to the right file.
Unlocks
Automatic docs preview
The documentation page isn't written by hand — it's generated from that same registry entry.
Unlocks
Discord sharing
Specs and preview pulled automatically from the registry entry, not copied by hand into the message.
Notes

This is the central argument of the proposal: the value isn't in any single feature (the Diff, the v0 button, Cmd+K) — it's in the fact that they all share the same structured data source. Adding a new feature down the line (e.g. auto-generating tests) doesn't require collecting information again — it's already in the registry entry.

Entry 12 — The road to here

From open-source template to an in-house foundation, in three phases.

Starting point
Forked an open-source starter for shadcn/ui registries
Instead of starting from scratch, we built on a base already tested by the community — a speed decision, not a shortcut.
Phase 1
Compatibility with AI tools
Adjusted all 66 source components to work in external sandboxes (v0): exports, imports, and CSS variables normalized one by one.
Phase 2
Architecture and organization
Reorganized the components folder by domain, fixed the registry build, removed orphaned files.
Phase 3
Documentation and polish
Design specs per component, cataloged item types, export and sharing.
Notes

This entire journey — from the initial fork to the current state, around 26 commits — happened over a very short span, with an AI agent (Claude Code) supporting most of the implementation, review, and testing. That's a relevant data point for a technical audience: it shows maintaining this doesn't require a large dedicated team, and that the iteration pace can be high.

Entry 14 — What's missing

Being honest about the state of the POC.

Blocked
Figma Diff on the free tier
Figma's free API only reads published styles in a team library; the current file only uses local styles. Fixed with a Figma Professional plan — the switch to the Variables API is already mapped out and ready to implement.
In progress
Per-brand preview not wired up yet
The 38 per-brand component variants already exist in code, but the docs preview still only swaps CSS variables — the right component still needs to be wired to each theme tab.
Minor
One flagged spot of technical debt
One function's complexity sits above the linter's limit, documented with an explicit note in the code for a future refactor — doesn't block functionality.
